## Суть — самообучающийся ETL по паттерну «парсер не справился → карантин → LLM → доработка»

Целевое ARM-устройство (касса) автономно. GPU-машина — для обучения/подготовки модели.
Лёгкий детерминированный парсер работает оперативно; всё, что он не осилил, уходит в
карантин, и **on-device LLM дорабатывает** так, чтобы дальше читалось детерминированно.

Три уровня карантина (всё на устройстве):

1. **Известный формат** (EnterpriseData 1.x, CommerceML 2.05, документы) → встроенный
   Python-парсер (миллисекунды) → SQLite (42 таблицы, `db_writer_lite.py`, без ORM).
2. **Неизвестный ФОРМАТ** → карантин по структурному fingerprint → LLM размечает
   образцы → авто-генерация **YAML-парсера** → shadow-eval (F1) → promote. Дальше формат
   читается детерминированно за миллисекунды, LLM в оперативке не нужна.
   *Доказано на устройстве:* инопланетный OmniLedger → авто-`auto_*`-парсер ~2 мс, без LLM.
3. **Формат знаком, но часть ДАННЫХ не легла** (значение вне замкнутого enum) → **карантин
   данных** → `POST /heal-data` будит LLM → она курирует allowlist (`allow` валидный код /
   `map` опечатку) → отложенные записи **retry**. (Вариант А — построен и проверён на устройстве.)

## Что сделано

### Парсеры (`core/parsers/`)
- `enterprise_data.py` — 1С EnterpriseData версии 1.x (1.2 / 1.10 / 1.14 / 1.20), включая
  документы `Документ.ПоступлениеТоваровУслуг` (приходная накладная → `doc_accept_invoice`
  + позиции + контрагенты/юрлица/склады). Деньги в копейках, идемпотентные id строк.
- `commerceml.py` — 1С CommerceML 2.05.
- `yaml_engine.py` — интерпретатор YAML-описанных парсеров (для авто-сгенерированных).
- `base.py` + `__init__.py` — Parser ABC, router, discovery.

### Автопарсер форматов (`core/autoparser/`)
`sample_collector` (карантин по fingerprint) · `structure_analyzer` · `llm_service`
(жизненный цикл llama-server) · `yaml_generator` · `shadow_evaluator` (матч по
бизнес-ключам name/barcode/article/display_name — НЕ по синтетическим id) · `orchestrator`.

### Вариант А — самолечение ДАННЫХ (новое)
- `db_writer_lite.py`: enum-колонки валидируются по `config/value_allowlists.json` (ведёт
  LLM). Значение вне списка → **карантин данных** (`data/data_quarantine/`), не краш и не
  потеря; `map` подменяет; `allow_any` — открытая колонка (без gatekeeping). `held_summary()`
  / `retry_held()`. Запись в БД пачками по 500 (не вешать слабую флешку одной транзакцией).
- `core/autoparser/data_healer.py` + эндпоинт `POST /heal-data`: LLM смотрит карантинные
  значения + смысл колонки → решает allow/map → правит allowlist → retry.
- `config/value_allowlists.json`: `catalog_product.unit` → `allow_any` (OKEI — открытый
  домен в сотни кодов, принимаем любой). Механизм allow/map/healer остаётся для реально
  замкнутых enum.

### Сервисы на устройстве (`target_host/`)
- `api_service.py` — FastAPI `:8080`: `/ingest`, `/ingest/raw`, `/status` (вкл. `held`),
  `/formats`, `/trigger-tick`, `/heal-data`. LLM поднимается **подпроцессом** (без root),
  idle 1800 с.
- `viewer/app.py` — FastAPI `:8081`: статус, просмотр БД, выгрузка CSV, **веб-форма
  загрузки файла** `/upload` (имя файла с кириллицей — поддержано).
- `systemd/` — юниты; `arm_install.sh` — установщик от голого Linux.

### Модель
Qwen2.5-Coder, дообучена на ~9210 примерах (разнообразные форматы + синтетика 1С +
реальные ED) с компактным `system_prompt.txt`. Варианты 1.5B и 0.5B (Q4_K_M GGUF).
На устройстве — 0.5B (~380 МБ): легче по RAM, prefill быстрее; но как **разметчик
нестабильна на edge-случаях** (выдумывает id, путает редкие коды) — для высокой точности
нужна 1.5B или дообучение. Обучение/экспорт — `gpu_host/{1,2,3}_*.sh`.

## ⚠ Важно про целевое устройство

- ARM: Debian 11, RK3566, 4 ГБ RAM.
- **eMMC тестового устройства деградирует** (повреждения ФС, жёсткие зависания на записи).
  Обход на время тестов: БД и карантин в **RAM** (`data` → симлинк на `/dev/shm`), логи
  journald в RAM. **Для прод-устройства нужна исправная флешка**; реальное лечение —
  e2fsck + перепрошить/заменить eMMC.
