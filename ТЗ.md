# ТЗ: LLM ETL — конфигуратор-парсер данных 1С с дообучаемой моделью

## Назначение

Автономная локальная система, которая принимает данные из 1С (любые актуальные
конфигурации и платформы — УТ, УНФ, Розница, ERP, БП и т.д.) и раскладывает
их в SQLite-БД по фиксированной retail-схеме (см. `config/schema.sql`,
40+ таблиц).

## Архитектура в 11 пунктах (пользовательский язык)

1. На GPU-машине (RTX 5090) пишется **парсер** (встроенные форматы 1С на Python).
2. На GPU-машине пишется и обучается **локальная LLM** (Qwen2.5-Coder-1.5B + LoRA).
3. Обучение **всегда на машине с GPU**.
4. Упаковка в один deploy-пакет с **оркестраторами и системными сервисами**.
5. Готовится **простой веб-интерфейс** на ARM-устройстве (статус, БД, форматы).
6. Собирается **инструкция и установщик** одним bash-скриптом.
7. На ARM-машине устанавливается → **работает парсер автономно**.
8. Если парсер встретил **неизвестную структуру** → данные кладутся в **карантин** (`samples/`), запись в БД помечается как «требует уточнения».
9. Накопилось 5+ примеров одного формата → **запускается LLM на ARM** (on-demand, systemctl start). Может быть автоматически или с подтверждения пользователя.
10. LLM разбирает данные, **создаёт YAML-парсер** для нового формата (shadow-режим → 20 проверок → автопромоут). После завершения LLM **выгружается** (systemctl stop) — освобождается 1.5 ГБ RAM.
11. **Переобучение базовой LLM** (когда форматы стали сильно сложнее) — на GPU-машине отдельным скриптом, **редкие случаи** (раз в полгода). Новая .gguf модель переносится на ARM.

**Автономность клиента**: после первой установки ARM-машина не нуждается в GPU-машине вообще. Все «дообучения парсеров» делает сама.

Основной фокус — **товары** (catalog_product, catalog_variant, штрихкоды,
артикулы, цены, группы, маркировка, алкоголь). В дальнейшем —
все документы (накладные, чеки, кассовые смены, перемещения,
инвентаризация, переоценка).

По итогам обработки система выдаёт **отчёт** (что записано, что не записано,
какие позиции вызвали сомнения).

## Архитектура: три машины

### Машина 1 — рабочая (разработка ТЗ + код)
**Не используется в производстве**, только редактирование примеров на ранней
стадии (с UI разметки) или просмотр БД при отладке. Не нагружается.

### Машина 2 — GPU-сервер (RTX 5090, Ubuntu 24.04)
**Главная** машина для всех тяжёлых операций:
- разметка обучающих данных (UI Gradio)
- генерация синтетических 1С-выгрузок через детерминированный парсер
- обучение / дообучение моделей (QLoRA fine-tune)
- конвертация LoRA → merged → GGUF → Q4_K_M
- сборка deploy-пакета для ARM-устройства
- хранение версий моделей (etl_v1, v2, …)

### Машина 3 — целевая ARM (production)
- Linux (Debian/Ubuntu) ARM64
- **4 ГБ RAM, 64 ГБ диск**
- На ней живёт production-инстанс: модель + БД + visual UI
- Получает данные из 1С, раскладывает по таблицам
- Имеет интернет, **без VPN**, должна работать только с тем что привезли

## Модель

| Параметр | Значение |
|---|---|
| Базовая модель | Qwen2.5-Coder-1.5B-Instruct |
| Формат деплоя | GGUF Q4_K_M (~940 МБ) |
| RAM при работе | ~1.5 ГБ |
| Движок | llama.cpp (нативно собранный под ARM64) |
| Размер LoRA-адаптера | ~150 МБ |
| Скорость обучения | ~10 сек на 10 примеров (RTX 5090) |

## Обучающий цикл (continual learning)

1. Накопить новые примеры (вручную через UI или авто-разметкой большой моделью)
2. Прогнать через `gpu_host/2_train.sh` — fine-tune LoRA, **подмешать 20% старых
   примеров (replay buffer)** чтобы не забыть прошлые форматы
3. Экспорт `gpu_host/3_export_gguf.sh` → новый `.gguf`
4. Eval-gate: если F1 на holdout-сете ≥ предыдущей версии, версия promotion'ится
5. Скопировать на target-устройство (флешка/сеть) → `target_deploy_model.sh`
6. Перезапуск сервиса

## Deploy-пакет для ARM

Один архив, всё что нужно для голой Linux-машины:
- `etl-parser-q4_k_m.gguf` (модель, ~940 МБ)
- `llama.cpp/` (исходники, компилируется на устройстве — ~10 минут)
- `database/schema.sql` + пустая `etl.db`
- `viewer/` — minimal web UI на datasette/Flask для просмотра БД
- `systemd/` — юниты для llama-server и viewer
- `install.sh` — single command install (apt install + cmake + systemctl enable)

После установки на ARM работают **два сервиса**:
- `llm-etl.service` — llama-server на порту 8080 (LLM-парсер)
- `llm-etl-viewer.service` — веб-просмотрщик БД на порту 8081

## Источники данных 1С

**Основной формат: EnterpriseData** (XML внутреннего обмена 1С 8.3).
Поддерживается **три версии**: 1.2, 1.10, 1.20 — у каждой свои нюансы тегов.
Это «родной» формат конфигураций УТ, ERP, БП, КА, УНФ, Розница.

Покрытие через EnterpriseData:
- Справочник.Номенклатура (товары, услуги, характеристики)

- Справочник.ШтрихкодыНоменклатуры (баркоды)
- Справочник.МаркиНоменклатуры + ОписаниеМаркированнойПродукции (ЧЗ)
- Справочник.Контрагенты, Справочник.Организации (юр.лица, ИНН/КПП)
- Справочник.Склады, Справочник.КассыККМ
- Справочник.ПрайсЛист + ПозицияПрайсЛиста (цены)
- Справочник.СерииНоменклатуры (партии алкоголя/маркированных)
- Справочник.СоставНабора (BOM наборов)

## Что должен дать пользователю отчёт после парсинга

JSON или HTML с разделами:
- **Записано**: N товаров, M вариантов, K штрихкодов (по таблицам)
- **Пропущено (дубликаты)**: список с ID
- **Ошибки**: что не распарсилось — фрагмент входа + причина
- **Низкая уверенность**: записи которые модель не уверена (logprob < порога) —
  отправить на ручную проверку

## Критерии готовности

- [ ] Качество: на holdout 50+ реальных 1С-XML F1 ≥ 0.85 по полям товара
- [ ] Производительность на ARM: ≥ 5 товаров/сек (sustained)
- [ ] Память: ≤ 2 ГБ RAM в пике
- [ ] Размер deploy-пакета: ≤ 1.5 ГБ
- [ ] Установка на ARM: один скрипт, ≤ 20 минут от чистого Linux
- [ ] UI просмотра БД: видны все 40+ таблиц + поиск по товарам/штрихкодам
